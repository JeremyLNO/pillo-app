# Pillo

Native iOS app for tracking birth-control pill intake, built for **CrazyBeeLabs**. Local-first: reminders work fully offline, no account required, no server dependency for the core loop.

## Stack

Swift 6 · SwiftUI · Swift Concurrency (async/await) · SwiftData · UserNotifications · WidgetKit (Home Screen, Lock Screen, and watchOS complications) · WatchConnectivity · StoreKit (review prompt) · LocalAuthentication (Face ID/Touch ID) · OneSignal (announcements/update pushes only — never the pill reminder) · String Catalog (fr/en/es/de/pt) · XCTest/XCUITest.

Minimum target: iOS 17, watchOS 10. No third-party UI frameworks.

## Targets

Six native targets, all generated by `gen_pbxproj.py` (see "Building" below):

| Target | Type | Purpose |
|---|---|---|
| `Pillo` | iOS app | The app itself |
| `PilloTests` / `PilloUITests` | Test bundles | See "Running the tests" |
| `PilloWidgetsExtension` | iOS widget extension | Home Screen (small/medium/large) + Lock Screen widgets, embedded in `Pillo.app/PlugIns/` |
| `Pillo Watch App` | watchOS app | Minimal read-only companion (no dose-confirmation UI — see "Watch scope" below), embedded in `Pillo.app/Watch/` |
| `PilloWatchComplications` | watchOS widget extension | Watch face complications, embedded in `Pillo Watch App.app/PlugIns/` |

### Watch scope: complications-only, by design

The Watch app is intentionally minimal — a read-only "next dose" view plus complications, not a second place to manage doses. Confirming a dose only happens on the iPhone or from the iOS widget's interactive button. This keeps the watch-side data flow one-directional and simple: no write path, no conflict resolution between two devices editing the same `DoseEvent`.

## Data sharing architecture

- **iOS app ↔ iOS widget**: both linked against the exact same on-disk SwiftData store, via `ModelConfiguration(groupContainer: .identifier("group.company.lno.pillo"))` (`Shared/Persistence/PersistenceController.swift`). The widget's "mark as taken" button (an `AppIntent`, see `PilloWidgets/MarkDoseTakenIntent.swift`) writes to this store directly — not a copy.
- **Widget display data**: computed once by the phone app (`Core/Services/WidgetBridge.swift`, needs `PillScheduleCalculator` so it isn't shared into the widget) into a small `WidgetSnapshot` struct, cached in the same App Group's `UserDefaults` (`Shared/CrossPlatform/WidgetSnapshotStore.swift`). The widget's `TimelineProvider` just reads this cache — no SwiftData query, no scheduling recomputation, on every timeline refresh. `WidgetBridge.refresh` runs after every dose mutation (`DoseChangeNotifying` notification, posted by `DoseTrackingService`) and on every app foreground.
- **iPhone → Watch**: the Watch is a *different physical device* — it cannot see the iPhone's App Group container at all. `Core/Services/WatchConnectivityService.swift` pushes the same `WidgetSnapshot` shape to the paired Watch via `WCSession.updateApplicationContext`; `PilloWatchApp/WatchSessionReceiver.swift` receives it and writes it into the *Watch's own, separate* local App Group (same group identifier string, physically distinct storage — one per device), which `PilloWatchComplications`'s `TimelineProvider` then reads.

## Architecture

```
App/              @main entry point, RootView (onboarding gate, lock gate, deep links), MainTabView
Core/                                                             App-only — not compiled into any extension
  Configuration/  AppConfiguration (reads xcconfig-sourced Info.plist keys), AppEnvironment
  Localization/   LocalizationService, LanguageResolver (pure, unit-tested), AppLanguage
  Navigation/     Route, DeepLinkRouter (pillo:// scheme, URL-validated)
  Notifications/  LocalNotificationService (sliding window), NotificationDelegate, BackgroundRefreshTask
  Persistence/    ServiceContainer (DI root), PersistenceController+Preview (demo data)
  Security/       BiometricLockService (Face ID), AppLockService (PIN, Keychain), KeychainStore
  Services/       PillScheduleService (+ pure PillScheduleCalculator), RuleEngineServicing,
                  StockService, OneSignal/, UpdateAvailabilityService, HistoryExportServicing,
                  DataExportServicing, URLValidator, WidgetBridge, WatchConnectivityService
Shared/                                    Compiled into every target (app + widget + watch app + complications)
  Models/         SwiftData @Model types (PillProfile, DoseEvent, NotificationPreferences,
                  StockEntry, SymptomEntry, UserPreferences, CustomScheduleDay)
  Services/       DoseTrackingService (+ its protocol, + LocalNotificationServicing protocol)
  Persistence/    PersistenceController (App-Group-backed SwiftData container)
  DesignSystem/   Palette, Typography, BlisterCell — uses UIColor, so NOT compiled into watchOS
                  targets (only into the app + iOS widget extension)
  CrossPlatform/  AppGroup, WidgetSnapshot, WidgetSnapshotStore — UIKit-free, safe on watchOS too
Features/         One folder per screen: Onboarding, Home, BlisterPack, MissedPill, History,
                  Stock, Symptoms, Settings, ReviewRequest, Account
PilloWidgets/     iOS widget extension: bundle, TimelineProvider, Home/Lock Screen views, AppIntent
PilloWatchApp/    watchOS companion app: entry point, read-only home view, WCSession receiver
PilloWatchComplications/  watchOS widget extension: complications for every accessory family
Resources/        Localizable.xcstrings, Assets.xcassets (shared into every target's Resources phase)
Tests/            XCTest unit tests (runs injected into the Pillo.app process — see below)
UITests/          XCUITest UI tests
Config/           .xcconfig files (Base/Debug/Staging/Release)
```

`Shared/DesignSystem` depends on `UIColor` (via `Color(uiColor:)` for light/dark dynamic colors), which doesn't exist on watchOS — that's *why* it's split from `Shared/CrossPlatform`, not just folder tidiness. If you add a new file to `Shared/` and it needs to compile on watchOS too, it has to avoid UIKit entirely.

**Dependency injection**: every service is defined behind a protocol (`XServicing`) with one concrete implementation. `ServiceContainer` builds them all once in `PilloApp.init()` and exposes them to the view tree via `@Environment(\.services)`. Tests construct services directly with an in-memory `ModelContext` — the container is never required in test code.

**Concurrency**: services touching `ModelContext` are `@MainActor`. Pure logic (`PillScheduleCalculator`, `SemanticVersion`, `LanguageResolver`, `URLValidator`) has no actor affinity and is fully unit-testable in isolation.

No Xcode GUI is used to maintain the project file — see "Building" below.

## Configuration variables

All in `Config/Base.xcconfig` (environment files `Debug`/`Staging`/`Release.xcconfig` only override `APP_ENVIRONMENT`). Values flow: xcconfig → `Info.plist` (`$(VAR)` substitution) → `AppConfiguration` (reads `Bundle.main`).

| Variable | Purpose | Status |
|---|---|---|
| `APP_NAME` | Display name | Set |
| `BUNDLE_IDENTIFIER` | `company.lno.pillo` | Set |
| `APP_STORE_ID` | Numeric App Store Connect ID | **TODO** — placeholder `0000000000` |
| `APP_STORE_URL` / `APP_STORE_REVIEW_URL` | Derived from `APP_STORE_ID` | Auto |
| `ONESIGNAL_APP_ID` | OneSignal dashboard App ID | **TODO** — placeholder, SDK no-ops until set |
| `CRAZYBEE_WEBSITE_URL` | `https://crazybeelabs.com/` | Set |
| `CRAZYBEE_SUPPORT_URL` | `https://crazybeelabs.com/support/` | Set |
| `CRAZYBEE_ACCOUNT_URL` | Falls back to website root — no dedicated signup page yet | **TODO** once one exists |
| `PRIVACY_POLICY_URL` / `TERMS_URL` | Legal pages | **TODO** — pages not published yet |
| `REMOTE_CONFIG_URL` | Update-check JSON (see `docs/ONESIGNAL_SETUP.md`) | **TODO** — empty until hosted |

> **xcconfig gotcha**: `//` starts a comment in `.xcconfig` files, which would silently truncate any `https://...` value. Every URL above is written as `https:$()//...` — the empty `$()` build-setting reference keeps the two slashes from being literally adjacent to the parser. Keep this pattern for any new URL you add.

## Associated Domains (Universal Links)

Not yet enabled — the `pillo://` custom URL scheme (already configured, see `App/Info.plist`'s `CFBundleURLTypes`) covers deep links today. To add Universal Links later:

1. Host `https://crazybeelabs.com/.well-known/apple-app-site-association` (no extension, `Content-Type: application/json`) with your Team ID + bundle ID (`TEAMID.company.lno.pillo`) and the paths to route.
2. Add the `com.apple.developer.associated-domains` entitlement with value `applinks:crazybeelabs.com` in `App/Pillo.entitlements`.
3. Re-run `python3 gen_pbxproj.py` — no script changes needed, entitlements are read from the file directly.
4. Verify the AASA file with Apple's [validator](https://search.developer.apple.com/appsearch-validation-tool/) before shipping.

This wasn't enabled from the start because it requires real hosting + a provisioned Team ID to test — enabling the entitlement without a working AASA file would silently break, not just no-op.

## URL Scheme

`pillo://` is registered in `App/Info.plist`. Routes handled by `Core/Navigation/DeepLinkRouter`: `home`, `today`, `history`, `settings`, `update`, `support` (opens the system browser), `pill/missed`. Every incoming URL — from a tap, from a OneSignal push, from `REMOTE_CONFIG_URL` — is validated by `URLValidator` before being acted on (`pillo://` scheme or an allow-listed `https://` host only). Deep links never bypass the biometric lock: if the app is locked when a URL arrives, `RootView` queues it and applies it only after a successful unlock.

## StoreKit

The review prompt uses the system `@Environment(\.requestReview)` action (`RootView.maybeRequestReview()`), gated by `ReviewRequestServicing` (first launch to app-usable state, ≥24h since install, never asked twice). No custom Yes/No dialog, no `.storekit` configuration file needed for this (in-app purchases aren't part of Pillo). If IAPs are ever added, generate a `.storekit` file via Xcode's File ▸ New ▸ File and reference it from the scheme's Options tab.

## Building

No Xcode GUI is used to create or maintain the project file — `gen_pbxproj.py` deterministically regenerates `Pillo.xcodeproj/project.pbxproj` (and the shared scheme) from the filesystem every time.

```bash
python3 gen_pbxproj.py   # regenerate the Xcode project from source
./build-run.sh           # build, install, and launch on a simulator (default: iPhone 17 Pro)
PILLO_DEVICE="iPhone 16" ./build-run.sh   # override the simulator
```

You can also open `Pillo.xcodeproj` in Xcode after running `gen_pbxproj.py` — just re-run the script (not Xcode's own project editor) whenever you add/remove/rename a source file.

> **Multi-platform gotcha**: don't pass `-sdk iphonesimulator` (or any single `-sdk`) to `xcodebuild` for this project. The `Pillo` scheme now embeds a watchOS app + complications alongside the iOS app; forcing one global SDK makes *every* target — including the watchOS ones — compile against it, which fails (`'accessoryCorner' is unavailable in iOS`, wrong icon format, etc.). Pass `-destination` only and let each target resolve its own platform from its own `SDKROOT`.

### Verifying the widget/watch targets specifically

```bash
# Confirm the nested embedding actually happened (widget in the app, watch app in the app, complications in the watch app):
find build -name "*.appex" -o -name "Pillo Watch App.app"

# Confirm the system actually recognizes the installed widget extension as a plugin:
xcrun simctl spawn <device-id> pluginkit -m -i company.lno.pillo.widgets
```

Visually confirming the widget in the Home Screen/Lock Screen gallery, and confirming watchOS complications render on an actual paired Watch Simulator, both require interactive steps (long-press → Edit Home Screen → search, or Xcode's Watch Simulator pairing flow) that aren't scripted here — do that once in Xcode/Simulator after a source change that touches `PilloWidgets/` or `PilloWatchComplications/`.

## Running the tests

```bash
DEV_ID=$(xcrun simctl list devices available | grep "iPhone 17 Pro" | head -1 | grep -oE '[0-9A-F-]{36}')
xcodebuild -project Pillo.xcodeproj -scheme Pillo -destination "id=$DEV_ID" -only-testing:PilloTests test
xcodebuild -project Pillo.xcodeproj -scheme Pillo -destination "id=$DEV_ID" -only-testing:PilloUITests test
```

`Tests/` covers the schedule/blister-pack algorithm (all 5 schedule types), dose confirmation/undo/correction, SemVer comparison, URL validation, language-fallback priority, stock math, PIN lock, review-request timing, the update-availability decision logic (mocked network), and the widget data pipeline (`WidgetBridgeTests` — runs injected into the `Pillo.app` process via `TEST_HOST`, so it inherits the app's real App Group entitlement and round-trips an actual `WidgetSnapshot` through the same shared `UserDefaults` suite the widget extension reads). `UITests/` drives the real app: full onboarding with an explicit notification-permission refusal, tab-by-tab rendering, a dose confirmation propagating live across Home/Plaquette, language switching without relaunch, and dark mode / accessibility Dynamic Type smoke checks.

## Creating a Production build

1. Fill in the real `APP_STORE_ID`, `ONESIGNAL_APP_ID`, and legal-page URLs in `Config/Base.xcconfig` (or override in `Config/Release.xcconfig` if they should differ from Staging).
2. Set `App/Pillo.entitlements`'s `aps-environment` to `production` for the Release configuration if App Store Connect doesn't rewrite it automatically during archiving (it usually does, based on the distribution provisioning profile — verify after archiving).
3. `python3 gen_pbxproj.py`
4. Archive: `xcodebuild -project Pillo.xcodeproj -scheme Pillo -configuration Release -sdk iphoneos archive -archivePath build/Pillo.xcarchive` (requires a real Development Team / provisioning profile — the `2E6D4Q69QB` team ID in `Config/Base.xcconfig` is this dev account's; replace with the shipping team's ID).
5. Export/upload via Xcode Organizer or `xcodebuild -exportArchive`.
6. Walk `docs/APP_STORE_CHECKLIST.md` before submitting.

## What's deliberately not done yet

- **No real medical missed-pill rules.** `Core/Services/RuleEngineServicing.swift` defines the exact rule shape from the spec (ruleID, medicalSource, reviewedBy, medicalReviewDate, etc.) and `FallbackRuleEngine` always returns the safe generic fallback message. Populating real rules requires a licensed medical reviewer — see `docs/MEDICAL_RULE_GUIDE.md`. Never fill this with LLM-generated content.
- **No Universal Links** (Associated Domains) — needs real hosting, see above.
- **App icon**: both the iOS and watchOS `AppIcon.appiconset`s use the honey/blister-pack design (single 1024×1024 full-bleed source, no pre-baked corner rounding — iOS/watchOS apply their own mask). Swap the source PNG and re-run `sips -Z 1024 <new.png> --out .../AppIcon-1024.png` for both `Resources/Assets.xcassets/AppIcon.appiconset/` and `PilloWatchApp/Assets.xcassets/AppIcon.appiconset/` if it changes again.
- **CrazyBeeLabs account creation has no in-app auth** — the Settings row opens the website; per spec section 19 this is intentional for v1 (no email collection in-app).
- **Watch app is read-only by design** (see "Watch scope" above) — confirming a dose only happens on the iPhone or from the iOS widget's button, never from the Watch.
- **No real-device App Group / Watch pairing tested** — everything above is verified in Simulator (nested embedding structure, widget registered as a system plugin, the full snapshot data pipeline via `WidgetBridgeTests`). A real device needs the `group.company.lno.pillo` App Group actually provisioned for both the iOS and watchOS App IDs in the Apple Developer portal before `ModelConfiguration(groupContainer:)` and `WCSession` will work there — Simulator is more lenient about this than a real device with real provisioning profiles.
